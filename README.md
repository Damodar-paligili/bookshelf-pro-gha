# 🏦 VeeraBank — Cloud-Native Banking Microservices on AWS EKS

A production-style, event-driven banking platform: **20 independent FastAPI microservices**, a static JS frontend, and **3 event-driven Lambda functions**, provisioned entirely by **Terraform** and deployed to **Amazon EKS** via **GitHub Actions**.

## 🏛 Architecture Overview

* **Frontend**: Static HTML/CSS/JS single-page dashboard, served via Nginx.
* **Backend**: 20 independent FastAPI microservices (Python 3.12), one per banking domain — accounts, transactions, transfers, cards, loans, payments, beneficiaries, statements, notifications, kyc, fixed-deposits, cheques, disputes, audit-log, fraud-detection, support-tickets, rewards, admin, reports, chatbot.
* **Shared backend code**: `backend/common/` — `service_base.py` (shared FastAPI app factory/middleware), `aws_clients.py` (boto3 client helpers), `mailer.py` (SES helper).
* **Primary datastore**: Amazon DynamoDB — one table per domain (`accounts`, `transfers`, `users`, `otp_codes`, plus a generic table pattern for the remaining services), each with GSIs for lookup by user/account.
* **Relational replica**: Amazon Aurora MySQL cluster (writer + reader instance) — a read replica of the `users` DynamoDB table, kept in sync by the `users_db_sync` Lambda via DynamoDB Streams. Credentials are generated by Terraform (`random_password`) and stored as a JSON object in a private, encrypted S3 bucket.
* **Event-driven Lambdas**:
  - `transactions_history` — API Gateway-fronted Lambda that reads/writes per-user activity history in S3.
  - `notification_writer` — writes outbound notifications, feeding SES for email delivery.
  - `users_db_sync` — DynamoDB Streams-triggered, keeps the Aurora `users` table in sync with DynamoDB.
* **Object storage**: S3 — transaction/activity history (`transaction_history` bucket, partitioned per user/account) and the Aurora credentials object.
* **Messaging/notifications**: SNS (topics) + SES (email identity) for outbound notifications.
* **Container registry**: Amazon ECR — one repository per microservice, created dynamically from the service list in Terraform (`ecr.tf` / `services.tf`).
* **Container orchestration**: Amazon EKS with managed node groups, plus:
  - IRSA (IAM Roles for Service Accounts) for the AWS Load Balancer Controller, the EBS CSI driver, and the backend app's DynamoDB/S3 access — no static AWS keys inside pods.
  - AWS Load Balancer Controller provisions an ALB from the `Ingress` resource, path-routing each `/service-name` prefix to its corresponding ClusterIP service, with `/` routed to the frontend.
* **Networking**: Custom VPC (`10.20.0.0/16`) across 2 AZs (`us-east-1a`/`us-east-1b`), public + private subnets, 1 Internet Gateway, 1 shared NAT Gateway. The VPC module is written to detect and reuse an existing tagged VPC if one already exists (useful in AWS accounts capped at 1 VPC/region).
* **CI/CD**: A single GitHub Actions workflow (`.github/workflows/deploy.yml`) with two jobs — `terraform` (bootstraps state, applies infra, exposes outputs) and `deploy` (builds/pushes all 21 images to ECR, renders k8s manifests with the Terraform outputs substituted in, syncs secrets, applies manifests, waits for rollout, prints the ALB URL).

## ⚙️ Prerequisites

* An active AWS account with sufficient IAM permissions (an IAM user, not root — `AdministratorAccess` is fine for learning).
* AWS CLI installed and configured locally (`aws configure`).
* Terraform, kubectl, and Docker installed locally.
* A GitHub account hosting your own copy of this repository.

## Step 1: GitHub Repository Setup

```bash
cd banking-microservices-k8s
git init
git branch -M main
git add .
git commit -m "Initial commit: VeeraBank EKS banking microservices project"
git remote add origin https://github.com/<YOUR_GITHUB_USERNAME>/<YOUR_REPO_NAME>.git
git push -u origin main
```

> Add a `.gitignore` **before** your first commit covering `__pycache__/`, `*.pyc`, `.terraform/`, `*.tfstate*`, `.tfstate-bucket-name`, `.env`, and `node_modules/` — none of these belong in version control.

## Step 2: AWS CLI & Terraform State Bootstrap

Configure the CLI with an IAM user's access key:

```bash
aws configure
# AWS Access Key ID: <yours>
# AWS Secret Access Key: <yours>
# Default region name: us-east-1
# Default output format: json
```

Verify:

```bash
aws sts get-caller-identity
```

The repo ships with a placeholder S3 backend bucket name that belongs to the original project's AWS account — you cannot use it. Generate your own:

```bash
chmod +x scripts/bootstrap-state.sh
./scripts/bootstrap-state.sh
```

This creates a uniquely-named S3 bucket (using your AWS account ID), enables versioning/encryption/public-access-block on it, creates the `veerabank-terraform-locks` DynamoDB lock table, rewrites `terraform/main.tf`'s backend block to point at your new bucket, and runs `terraform init -reconfigure`.

---

## Step 3: Provision Infrastructure with Terraform

From the `terraform/` directory:

```bash
cd terraform
terraform plan
terraform apply
```

This provisions, in one pass: the VPC and networking, the EKS cluster with IRSA roles, all 21 ECR repositories, the DynamoDB tables, the Aurora MySQL cluster + credentials object, the S3 buckets, the SNS topic, the SES identity, and the 3 Lambda functions + API Gateway.

> To inspect a single layer before committing to the full apply, scope it with `-target`, e.g. `terraform plan -target=module.vpc` — but treat `-target` as a debugging tool, not routine workflow.

Once complete, connect `kubectl` to the new cluster:

```bash
aws eks update-kubeconfig --region us-east-1 --name $(terraform output -raw eks_cluster_name)
```

## Step 4: GitHub Secrets & CI/CD Pipeline

In your GitHub repository: **Settings → Secrets and variables → Actions → New repository secret**. Add:

| Secret Name | Description |
|---|---|
| `AWS_ACCESS_KEY_ID` | IAM user access key |
| `AWS_SECRET_ACCESS_KEY` | IAM user secret key |
| `SMTP_USER` | Gmail address used for outbound notification email |
| `SMTP_APP_PASSWORD` | Gmail app password (not your account password) |
| `GROQ_API_KEY` | API key for the chatbot service's LLM calls |

The workflow (`.github/workflows/deploy.yml`) triggers on push to the **`master`** branch, or manually via `workflow_dispatch`. It runs two jobs in sequence:

1. **`terraform`** — ensures the state bucket/lock table exist (self-healing if the bucket name is transiently unavailable), runs `terraform init && terraform apply`, and exposes outputs (cluster name, ECR URLs, etc.) to the next job.
2. **`deploy`** — logs in to ECR, builds and pushes all 21 service images, updates the kubeconfig, renders the k8s manifests substituting in the real Terraform outputs, syncs the `app-secrets` Secret from the GitHub secrets above, applies all manifests, waits for rollouts, and prints the final ALB URL.

> Note: if your default branch is `main` rather than `master`, either rename your branch to `master` or update the `on.push.branches` trigger in `deploy.yml` to match — otherwise pushes won't trigger the pipeline automatically (you can still run it manually via `workflow_dispatch`).

## Step 5: Kubernetes Deployment Details

* **Namespace**: everything deploys into `veerabank`.
* **ServiceAccount**: `backend-app`, annotated with the IRSA role ARN from `terraform output backend_irsa_role_arn` — this is how pods get DynamoDB/S3 access without embedding AWS keys.
* **Secrets**: `k8s/app-secrets.example.yaml` is a template only — never fill it in and commit it. The CI pipeline creates the real Secret at deploy time from GitHub Actions secrets.
* **Ingress**: a single ALB, path-routed — `/accounts`, `/transactions`, `/users`, `/transfers`, `/cards`, `/loans`, `/payments`, `/beneficiaries`, `/statements`, `/notifications`, `/chatbot`, `/kyc`, `/fixed-deposits`, `/cheques`, `/disputes`, `/audit-log`, `/fraud-detection`, `/support-tickets`, `/rewards`, `/admin`, `/reports` each route to their respective ClusterIP service, with `/` routed to the frontend. Health checks hit `/healthz` on each service.

## Step 6: How to Access & Verify the Application

Retrieve the ALB hostname:

```bash
kubectl get ingress veerabank-ingress -n veerabank
# or, once ready:
kubectl get ingress veerabank-ingress -n veerabank -o jsonpath="{.status.loadBalancer.ingress[0].hostname}"
```

Open `http://<ALB-HOSTNAME>` in a browser (allow 1–2 minutes for DNS propagation and ALB health checks on first launch). Verify end-to-end: register a user, log in, open an account, perform a transfer, and confirm it shows up in statements/transactions.

```bash

# Logs for a specific service
kubectl logs -l app=accounts -n veerabank --tail=100 -f

# Restart a specific service
kubectl rollout restart deployment/accounts -n veerabank

# Describe the ingress (check ALB provisioning/target group health)
kubectl describe ingress veerabank-ingress -n veerabank

# Check IRSA is wired correctly
kubectl get sa backend-app -n veerabank -o yaml
```

## 🧹 Infrastructure Teardown (Clean-Up)

To avoid ongoing charges (EKS control plane, NAT Gateway, Aurora instances are the main cost drivers):

```bash
# Remove k8s-created ALB/load balancer resources first, so Terraform can clean up ENIs/security groups
kubectl delete ingress veerabank-ingress -n veerabank

cd terraform
terraform destroy
```

Then, if you no longer need them, manually delete the Terraform state S3 bucket and the `veerabank-terraform-locks` DynamoDB table (Terraform won't delete its own backend).
